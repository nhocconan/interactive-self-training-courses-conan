Operating AI Agents
Observe · Ground · Act · Verify

Learn to record the current state, pick your data source, split work by reversibility, and check output against evidence. This course is about how to operate agents — not how to write prompts or code.

Start learning → See the curriculum
Tool names and numbers here are illustrative

The products used as examples include ChatGPT (Chat/Work/Codex), Claude (Chat/Cowork/Claude Code), and apps/connectors such as Drive, Slack, and Sheets. Features and model names can change, so each lesson always states the selection criteria and not just a tool name. Likewise, every domain (crm-staging.example.test), number, and scenario is a made-up example for learning — not a real system or real data.

What this course covers

Output can be wrong because data is missing, the request is vague, permissions fall short, a tool breaks, or the model reasons poorly. This course focuses on the part you can control: inputs, permissions, stop points, and the checks you run on the output.

Module 01 · Part I · Foundations

A map of four surfaces, permissions, and remote control

This module separates Chat, Work/Cowork, code tools, and Browser/Computer Use; then it sets permissions, spots hidden instructions, and uses Voice/Remote without dropping the gates.

Lesson 1.1

The four AI surfaces

By the end of this lesson you can
  • Name the four AI surfaces and the basic difference between them.
  • Pick the right surface for a specific job using two questions.
  • Spot the signs of "using the wrong surface" before the damage lands.

You just handed the AI a job: migrate 247 customers from a Sheet into a CRM. It runs for 40 minutes and reports "done". You open the CRM: there are exactly 20 rows. Not 247. You reopen the Sheet, the source data is untouched. You conclude: "AI is useless."

But the problem isn't quite that AI is useless. You may have used the wrong surface (the working environment where you hand off the job). Chat can create files, but a single message doesn't turn itself into a multi-step process with access, stop points, and evidence. Work that needs a finished artifact belongs on a surface that fits its data and its verification.

You don't have to memorize the whole table. Just ask two questions:

  • (1) Is the end result an answer, or a deliverable?

    An answer or a short draft → Chat. Multi-step work that needs files, changes state, or runs in the background → prefer Work/Cowork. Chat can still make files; the difference is how the work is organized and tracked.

  • (2) Does the target system have an API/connector, or must you drive the mouse?

    A connector (Drive, Slack, Sheets…) → use it, don't open Chrome. Web UI only → Browser Use; the whole machine → Computer Use (the last resort).

Choosing when several surfaces would work

Prefer the path with the narrowest access, the most structured data, and the result that's easiest to check. For example, if an admin-approved Drive app already serves the right file, there's no need to automate clicks on the Drive page.

In practice · two roles
▶Sales OpsSomeone asks "how many Q2 orders?"
The answer is a number → Chat is enough, just paste the 3 tables in. But if the same question repeats every week → move to Code (a scheduled script) or Scheduled Tasks in Work/Cowork (see Lesson 5.3).
▶DataMigrate 247 Sheet rows → CRM
This has to write into the CRM, so Chat only fits for planning or drafting rules. A CRM connector → Work/Cowork. Web UI only → Browser Use + prepare a safe workspace (Lesson 1.2).
Takeaway

Before switching models, re-check the surface: what the output needs, where the data lives, what the AI is allowed to do, and how the result will be checked.

Quick check

Every week you roll three Excel files into one summary. Right now you paste the three files into a chat and ask the AI to summarize. Which surface fits when this repeats weekly?

Lesson 1.3

Prompt injection & four emergency stop signals

By the end you can
  • Recognize instructions embedded in external content.
  • Separate prompting from containment.
  • Stop on signs of scope escape.

Synthetic scenario: an agent reads a comment on a price page that asks it to send customer data to an unfamiliar address. The text may be visible, in email or a file, or user content on a trusted site. Injection needs no hidden HTML and is not specific to web agents.

  • Use necessary sources and least-privilege accounts; separate sensitive data from outbound-send capability.
  • Enforce file/network/tool limits outside the prompt; test stopping, credential revocation and logging.
  • Stop and notify IT on an unexplained topic change, out-of-plan domain, password/OTP/card request or unfamiliar file recipient. Preserve evidence before recovery.

The joint ASD/international guidance of 1 May 2026 recommends low-risk initial uses and least privilege. The 12 November guidance specifically concerns AI cyber-capability testing environments; it is not a universal production standard. It emphasizes controls outside the model, monitoring and emergency shutdown.

  • Check local/cloud session permissions.

Module 02 · Part II · The backbone

The Observe · Ground · Act · Verify loop

Before you touch data, answer two questions: which source is the truth? and what proves it's done? The four-step loop forces both answers out before the change, then re-checks after. It's only "done" at VERIFY, not when the task reports done.

Lesson 2.1

OBSERVE: valid observational evidence

By the end you can
  • Choose evidence suited to the question.
  • Capture provenance and scope before writing.
  • Separate baselines from backups.

Synthetic example: “about 800 rows, looks valid” is insufficient as a migration baseline. Save source/target identity, time, filters, keys, original exports and count definitions before writing.

  • A screenshot records UI state/filter but does not prove all rows are included.
  • Complete exports and keyed field diffs check content; verify provenance, query/filter, time and completeness.
  • Logs/audit trails check actors and actions; logs can be incomplete and need target reconciliation.
  • A baseline supports comparison; a backup with tested restore supports recovery. Neither retracts data already sent outside.
Takeaway

Evidence needs correct scope and reproducibility; confident or cautious wording alone proves neither truth nor fabrication.

Quick check

You need to check 247 migrated email fields. What is the main evidence?

Lesson 2.2

GROUND: source of truth + field map + acceptance

By the end you can
  • Lock source, mapping and acceptance.
  • Partition source into accepted/rejected exactly once.
  • Check all keyed fields and protect pre-existing target data.

Synthetic scenario: source is blank and the agent fills Facebook. Without an approved inference rule, this violates the contract. It does not establish whether the cause was the brief, model or data; inspect the request and logs. Repair the missing-data rule and retest both missing and valid cases.

  • Source of truth: allowed sources and who resolves conflicts; an official record can still be stale.
  • Field map: columns, types, normalization, closed enums, required fields and duplicate-key policy.
  • Acceptance: complete checks on accepted rows and target, beyond counts or a few spot-checks.
Working template
MIGRATION CONTRACT
- Lock raw A + hash, field-map version, target environment/account and B baseline.
- Each source ID appears exactly once: clean OR rejected with a reason.
- clean has unique external_ref; rejected explains excluded source rows only.
- Compare every field by external_ref: clean vs job-scoped target => empty diff.
- No unexpected target keys; no out-of-scope changes to baseline records.
- Exclude the approved pilot from the remaining bulk.
- Write timeout => UNKNOWN; reconcile target before retry; state is not commit proof.
- Missing data/access/evidence => UNVERIFIED.
Takeaway

Rejections do not excuse errors in accepted rows; require an empty full keyed diff and correct source partition.

Lesson 2.3

ACT: split phases by reversibility

By the end of this lesson you can
  • Classify each action by its 3 levels of reversibility.
  • Split a write job into phases with their own scope and checkpoint.
  • Know when you need independent approval, a backup, or a switch to manual.

The situation. You ask the AI to delete 500 duplicate records in the CRM. Delete is irreversible: run all 500 at once and one wrong rule means 500 real rows gone. The safe way is to split actions by reversibility: try 1 row, get a reviewer, then widen.

Split phases by reversibility, impact and authority. Reads/exports can still disclose data through external services. Backups support file/record recovery; they do not retract sent email, exposed data or external transactions.

Level Action What's needed before running
Easily reversible Read/export within approved data scope; create a new file without overwrite Scope to the right folder/range; don't overwrite the source file
Hard to reverse Create a new record, upload a file, edit a field, change status Run 1 pilot row → a person confirms → then bulk
Irreversible Delete, send email/message, submit a binding form, make a payment A backup or recovery plan; independent approval per policy, or switch to manual
One pilot row catches errors before they scale

A pilot checks the field map, write permissions, and output format on a small scope. Widen only after the result meets the acceptance criteria and someone with authority approves.

When you need an independent approver

For hard-to-reverse or high-impact actions, an approver who isn't the runner catches assumptions and mistakes the doer might miss. This is one layer of control; it doesn't replace backups, logs, and permission limits.

Takeaway

Classify actions by reversibility and impact. Each phase needs a scope, a checkpoint, and an approval layer that fits your org's policy.

Quick check

The AI needs to delete 1,200 old records in the CRM staging to clean up before a fresh import. What kind of action is this, and what does it need?

Lesson 2.4

VERIFY: record evidence and four fast checks

By the end you can
  • Separate arithmetic consistency from data correctness.
  • Apply scoped count/diff/spot-check/screenshots.
  • Keep unverified status when evidence is missing.

Synthetic example: raw=247, clean=240, rejected=7; B starts empty and ends with 240 rows. The arithmetic 240+7=247 is correct but proves neither correct fields nor absence of unexpected keys. Five correct spot-checks do not replace checking all 240 accepted records.

  • Count within one scope: raw = clean + rejected; verify each ID exactly once, with no omissions/duplicates.
  • Diff: fresh complete scoped export, compared with clean by external_ref across every field; diff must be empty.
  • Baseline: protect pre-existing rows; check missing/unexpected keys and changes outside the job.
  • Spot-checks and same-filter screenshots complement machine checks; a record absent after reload requires ACL/filter/cache investigation before concluding it was not saved.
Takeaway

Accept migration only with a correct partition, empty full keyed diff and protected baseline.

Quick check

A report has 487/500, 13 rejected and 5 correct spot-checks. Accept yet?

Module 03 · Part III · Orchestration

Choosing the mode, model, and verification role

Pick the right surface first, then the model or reasoning level if the product allows it. Fast work uses Chat; long work needing a finished artifact uses ChatGPT Work or Claude Cowork; software uses Codex or Claude Code. For work with real consequences, add an independent verification thread.

Lesson 3.1

Pick the mode and model by job type

By the end you can
  • Choose the environment before the model.
  • Measure the same workflow and record configuration.
  • Check authority and impact before autonomy.

Choose the environment by data, access and output before model/effort. Try the available default on a representative labeled set. Local exercise: 100 comments covering common topics and hard cases, with a separate untouched set after prompt tuning. The size 100 is an exercise choice, not a standard threshold.

Record the session’s model, effort, client/version, tools, context and configuration. Work/Codex exposes model/effort controls; options vary by account/workspace/client. Avoid memorizing model names. An app and API using the same model name can differ in system prompts, tools and sampling; this is not a controlled experiment.

Lesson 3.2

Orchestrate three roles: plan · execute · verify

By the end you can
  • Sequence dependent phases.
  • Give a verifier sufficient inputs.
  • Limit parallelism by dependencies and review capacity.

Separate roles so the runner does not merely approve its own claims. For migration, normalize → write → export/verify are sequential dependencies; collect logs during execution. These are not three independent parallel workers.

  • Planner locks the spec, access and criteria; an authorized person approves before writes.
  • Runner writes a pilot, waits for approval, excludes it from bulk; reconcile UNKNOWN commits before retry.
  • Verifier receives raw, clean, rejected, mapping/criteria, baseline and a fresh export for the right account/scope. Independently computes partition and all keyed fields. An initial result check can precede the runner’s narrative to reduce anchoring; logs remain available for audit and diagnosis.
  • Parallelize only independent work with suitable access/data, no resource conflict and sufficient quota/review capacity. Different files alone are insufficient; two LLM threads are not statistically independent.
Takeaway

Separate checking from self-report without withholding logs, specifications or required data.

Lesson 3.3

Cost discipline: three ways to misuse a surface

By the end of this lesson you can
  • Spot three choices that can raise time or quota without improving the result.
  • Pick Chat or Work/Cowork by the output and the number of steps needed.
  • Decide when to continue the current session and when to split off a new one.

The situation. A task you run every week, and this month's AI bill tripled with no better result. It's usually the wrong surface: a short Q&A opened as a full Work session, or a high reasoning level left on for easy work. This lesson names three common ways to burn quota and how to re-measure.

Measure time, quota, and manual-fix effort per passing result. Revisit the three choices below when cost rises without a matching rise in quality.

3 quota-burning mistakes
  • Mistake 1 · Using Work/Cowork for a short answer. Without source access, multi-step actions, or an artifact needed, Chat answers more directly.
  • Mistake 2 · Always picking the strongest reasoning level. "High just to be safe" is an unmeasured assumption. Compare on the same test set before raising.
  • Mistake 3 · Unbounded sessions or full reruns. Context, caching, compaction and billing vary by product; not every turn bills the whole history again. Use reconciled state to reduce reruns and measure total cost per passing result.
Replace with
  • Short question → Chat. Work/Cowork is for multi-step jobs with a deliverable.
  • Start on the default; raise only when a test fails for lack of reasoning.
  • One job, one session: brief it properly → land it → close it. When the context fills up, compact deliberately or open a new session; don't let a session sprawl.

"One job, one session", and a five-line handover note

A handover can be short but must retain the goal, authority, decisions, files, verified state, remaining work and acceptance. Check it against artifacts; five lines is a suggestion, not a completeness guarantee.

A new session can lose omitted constraints while memory/project context may persist. If old assumptions interfere, record what was ruled out and verify inputs before continuing; a new chat is not a universal repair.

Measure per passing result

Compare options on the same test: completion time, quota or credits, re-run count, and manual-fix time. Token or call count alone doesn't show the full operating cost.

Takeaway

Choose the surface by output, set the model by measured results, and manage sessions by workstream. Track cost per passing result, including manual-fix time.

Module 04 · Part IV · In the field

Driving the browser and the computer

This module has two halves: (a) flows where the AI operates an interface — page state, authentication, slow loading, half-finished saves, and how to re-read the result after each action; and (b) one kind of output where counting and diffing catch nothing — a research report with citations (Lesson 4.3).

Lesson 4.1

Setup & the 6-step action loop

By the end of this lesson you can
  • Build the minimum safe configuration before you point an agent at the web.
  • Apply the 6-step loop: navigate → wait → read → type → validate → next.
  • Add a validate step that re-reads the state after a write action.

The situation. You ask the AI to go into an order-admin page (staging): filter the Pending orders, then move 30 of them to Shipping. The AI clicks away and, two minutes later, reports "updated 30 orders." You reopen it: 8 are still Pending, and 2 got moved on the wrong customer.

In this synthetic example, the report does not match target state. Stale UI, an overlay, autocomplete or a failed request are possible causes. This establishes neither the AI’s intent nor the root cause. Use the loop below to check each action.

Walk it through · move one order to "Shipping"

  • 1 · navigate → reach the right page

    Open the URL and confirm you're in the right place via a landmark (the "Order management" title, the "Filter" button). Trap: a stale link redirects to a login page the AI assumes it's past.

  • 2 · wait → wait for an element, not for seconds

    Wait until the order table has appeared, not "5 seconds then go." Trap: the table half-loads and the AI reads it at 12 of 50 rows.

  • 3 · read → read the current state

    Note it down: which filter is on, how many rows, the ID of the order to change, any popup in the way. Trap: a "survey" popup covers the Save button and the AI doesn't see it.

  • 4 · type → act on the right object

    Locate the order by its order ID (label), not by "the 3rd row" or coordinates. Trap: the table may re-sort, so "the 3rd row" may become a different customer's order. Check IDs and the action log before attributing the opening errors to this cause.

  • 5 · validate → re-read the result (the most-skipped step)

    Re-read that same order: is the status now "Shipping"? If the system stores server-side, reload and find it by ID. Different from expected → STOP, report.

  • 6 · next → only continue when step 5 passes

    Move to the next order only after validate passes. Skipping step 5 can leave failed or wrong updates undetected; it does not establish why the opening records differ.

6-step action loop · copy
1. navigate  → open the right URL, confirm you reached the right page (check the title or one landmark element)
2. wait      → wait for load to finish. NOT a fixed time — wait for an element to appear
3. read      → read the state: how many rows, which filter is on, is there a popup
4. type/save → enter by label; re-read the value, then Save only within approved authority
5. validate  → reload/find the authoritative record by ID and verify persisted fields.
                Mismatch or unknown commit → STOP, report; reconcile before retry
6. next      → only continue after both field and persisted-state checks pass
Validate is two checks, not one

After you type: re-read the field and compare to the intended value, autocomplete or a mask may have changed it. After you Save: reload or find the record by ID to confirm the server stored it. "Landed in the right box" and "durably saved" are different questions; skip either and you miss errors.

Set up before you let the AI run on a real site
Minimum configuration
  • A separate browser profile for the AI, not the profile holding banking/email/password-manager cookies
  • An IT-issued staging/demo account, not your prod
  • A separate machine or OS account if you run Computer Use at a high automation level
  • Keep a checkpoint on write actions; reduce it only after a pilot and once automated checks exist
Safe login pattern
  • A person logs in once, the AI inherits the session, the default pattern
  • Never paste a password into the chat box
  • Prefer a magic link or a narrow-permission demo account
  • On a captcha/payment, the agent stops and hands control back, that's correct, don't try to defeat it

Three buttons your hands must know

The six-step loop above is the agent's part. Your part is much smaller: three buttons, and all three have to be familiar enough that you press them without deliberating:

  • (1) Interrupt. If you see it go wrong at step 2, interrupt right there; don't sit through all ten steps first. Seven steps built on one wrong step are seven suspect steps.
  • (2) Steer. Once you've interrupted, say one sentence about exactly what's wrong: "the status column is column 4, not column 3". If you find yourself having to rewrite the whole brief to explain it, that isn't steering any more: that's the signal for button 3.
  • (3) Reassess. After repeated corrections, inspect the specification, access, state and tools. Restart with a verified handover if useful; the correction count does not prove context corruption.
The tool's undo covers less than you think

Claude Code /rewind (double Esc with empty input) restores files tracked by its file-editing tools. Bash-only files are untracked; later Bash changes to an already tracked file can be rewound. Foreground forked skills can be restored; other subagents and external edits depend on files already tracked by the parent. See Checkpointing (accessed 13 Nov 2026).

Keep a narrow write scope and a backup/commit with tested recovery. Rewind does not undo CRM changes, sent mail, transactions or exposed data.

Takeaway

The action loop ends with validate: re-read the field and, when needed, reload or find the record to confirm the server saved it.

Lesson 4.2

Eight typical failure modes

By the end of this lesson you can
  • Recognize the 8 failure modes specific to web agents.
  • Apply a fast check for each mode.
  • See how an unverified completion report can mask the other failures.

Synthetic scenario: the agent reports “processed 100 customers” without artifacts. Completion is unverified, with no cause established. The signs below are hypotheses to investigate, not diagnoses from wording or counts.

Failure mode What it is Sign + check
01 · Phantom save The AI clicks Save, sees the button change state, concludes it saved. The server returned a silent validation error. Check by ID through an authoritative source. If absent, inspect account, ACL, filters, cache and audit/request status; absence from one view does not prove it was never saved.
02 · Missing rows
Lazy load		 The page renders the first 20 rows, the rest load on scroll. The AI reads 20 and reports total = 20. Sign: a round number (20/25/50/100).
Check: compare against the UI total ("1-20 of 247"), or use an export instead of reading the screen.
03 · Wrong tab/environment Two tabs: staging and prod. The AI acts on the focused tab, not the one you think. Sign: the action succeeds but you don't see the result.
Check: make the AI print the full URL before every write action. Keep only 1 tab open during a write job.
04 · Popup over the button A cookie banner/modal/tooltip covers the button to click. The AI clicks the overlay. Sign: the agent repeats the same action with no state change.
Check: screenshot before every important click. Add a "close overlay" step at the top of the loop.
05 · Session expired A 40-minute job, session timeout at minute 25. After that, every request redirects to login. Sign: the URL changes to a login page, the account name disappears, or requests return auth errors.
Check: a checkpoint between batches: confirm the URL and a sign the session is still valid.
06 · Partial write A rate limit/network error cuts the batch. 120/247 rows landed, 127 didn't. No one knows the boundary. Record run_id + source hash + map version and stable operation keys; enforce unique external_ref at target. A write timeout is UNKNOWN: reconcile the target key and fields before retrying create-if-absent or guarded upsert, without overwriting existing rows. Last-row state is not remote commit proof. Exclude a committed pilot from bulk.
07 · Fabrication A required field, but the source is empty. The AI fills "N/A", "Not updated", or a plausible-sounding value. Sign: an empty source cell becomes a target value with no matching field-map rule.
Check: count empty cells per field and trace every difference back to an approved rule.
08 · Hallucinated completion The report concludes it's done but attaches no measurement or artifact you can check. Sign: the report uses general language ("all", "everything", "accurate") and has no number or file path.
Check: keep the status unverified and require evidence per the acceptance criteria.
A completion claim still needs evidence

Numbers and paths make a report easier to check; they do not prove it is true. “Migrated 240 customers” contains a count but no acceptance evidence. “237/240; 3 rejected; path X” also remains unverified until the files, source partition, full keyed diff and baseline checks support it.

Empty cells vanishing with no rule = stop

If the target has fewer empty cells than the source and the field map doesn't allow filling them, the AI may have filled them in itself. Compare empty-cell counts per field, every difference must trace to an approved rule.

Takeaway

The words "all/everything/accurate" aren't a failure by themselves. They're an unverified conclusion if the report has no matching number, artifact, and check.

Lesson 4.3

Verifying a research report

By the end of this lesson you can
  • Explain why counting and file comparison (Lesson 2.4) don't catch errors in a research report.
  • Back-check a sample of citations, separate fact from inference, and use an independent verification thread.
  • Treat any number you can't trace to a source as unverified, until proven otherwise.

The situation. The AI hands you a report: "Vietnam's e-commerce market grew 34% in 2025 (per Gartner)." You open the attached Gartner link: the page is real, but there's no 34% anywhere on it. This is the kind of error that count and diff (Lesson 2.4) can't catch: a research report isn't a data table, it's a chain of sourced claims, and you have to back-check each claim to its actual source.

Key concept

A research report is a chain of sourced claims

The four VERIFY checks in Lesson 2.4 (count · file-compare · sample-check · re-shoot) fit data results: there's a before/after count to subtract, a file to diff. A research report is different: a chain of claims, each attached (or not) to a source. Counting won't catch three errors: fabricated source (the link doesn't exist), fabricated number (the source is real but doesn't hold the cited number), and misquote (the source says it, but spliced out of context).

  • (1) Ask for sources from the start

    Every number or claim needs a link, an access date, and where it sits in the source. Phrases like "according to industry research" aren't enough for a reader to re-check.

  • (2) Back-check a sample of sources

    Pick N sources at random (say 3/12), open them yourself, find the exact number or claim in the original. The checker picks the sample to avoid selection bias.

  • (3) A number you can't trace to a source = unverified

    Don't use that number until you find the original or can recompute it. A missing source doesn't prove the AI made it up, only that you don't yet have a basis to trust it.

  • (4) Separate fact from inference

    Label each as "fact from a source" or "inference". This lets a reader see which sentence needs a source and which is interpretation.

  • (5) Important report → independent verification

    Give the checker a claim ↔ source ↔ location table and source content. Check that each claim is supported and separate fact from inference; a link list alone is insufficient. Reading conclusions after the first check can reduce anchoring.

A number with no source isn't enough to trust

Presentation doesn't prove content. A smooth, link-filled report can still misquote or splice context, judge each claim by its source, not the tone.

Request a claim ↔ source table · copy
Before writing the conclusion, output a table — one row each:
  claim | number | source (link) | access date | location in source
Location = the paragraph/sentence that holds that exact number.
Can't fill the "location" column = that claim is NOT checked yet, mark it [unchecked].
Every inference of yours (not from a source) → mark it [inference].
Don't write the conclusion until the table is complete.
Takeaway

For a research report, trace each claim back to its source, mark unverified numbers, and use an independent thread for important reports.

Quick check

A report has 12 citations. You back-check 3: 1 dead link, 1 live link that doesn't hold the cited number, 1 correct. What do you do?

Four layers of context

By the end of this lesson you can
  • Tell apart the 4 layers: Global · Folder · Project · Skill.
  • Put stable instructions at the right scope instead of copying them into every prompt.

The situation. Every time you hand off work, you paste the whole SOP into the prompt: required fields, how to handle exceptions, when to stop. Ten hand-offs, ten copies; fix one thing and you fix it in ten places. This lesson files the stable part into four context layers so you stop repeating it in every prompt.

A process often depends on unrecorded context: which fields are required, how exceptions are handled, when to stop, which evidence approves it. Save the stable part at the right scope so others can check and reuse it.

Layer What it holds When it applies
Global instructions

Lesson 5.3

Scheduled tasks and the tool priority order

By the end of this lesson you can
  • Tell apart work that may be scheduled from work that may not.
  • Choose tools by access, structured data and verifiability; treat the five tiers as a heuristic.
  • Set a team rule: every scheduled task has a named output reader + an alert threshold.

The situation. You schedule the AI to gather sales numbers at 8am daily and send a summary. Three weeks later you find the job has been failing since Monday: no one read it, there was no alert threshold. This lesson sets the must-haves for any scheduled job, and the tool-priority order when you schedule.

ChatGPT desktop scheduled tasks need the computer on and app running for local files. Web tasks use uploads/context and connections, not a folder directly on your computer. Team Tasks run in the cloud with authorized service-account connections. Eligible event triggers are on web/mobile, not desktop; event and time triggers cannot be combined in one task.

A difference between Work and Cowork worth remembering

Before scheduling, test the actual execution environment, data and runtime authorization. Claude cloud differs from legacy local Dispatch: cloud continues with the computer off; Dispatch needs an awake desktop/open app and is now limited to existing beta users. Each job needs an owner, checks, alerts and a stop/revoke path.

Check Scheduled tasks and Dispatch. Accessed 13 Nov 2026, content cutoff 12 Nov 2026.

May be scheduled
  • Compile a report from read-only sources
  • Clean up and rename files in OUTPUTS
  • Watch for changes and draft an email (unsent)
  • Scan public data, output a comparison table
  • Prepare a pre-meeting brief
Not scheduled by default
  • Any write action into prod
  • Auto-send email/messages externally
  • Delete, even temp files
  • A job with no hard stop or no recovery/reconciliation design for its writes
  • A job no one is assigned to read the result of

This is a sample course policy. Archiving may support recovery but still requires destination, overwrite, retention and authority checks; reversibility alone does not authorize scheduling.

A required rule for every scheduled task

Every scheduled task needs a named person reading the output, and an anomaly threshold that alerts on its own (e.g. "if row count differs by more than 5% from last week, alert instead of the normal report"). A job can run fine 99 times and break on the 100th, if no one reads it, the incident surfaces weeks later.

Choose tools by the workflow, not a fixed ranking

  • 1 · Connector / MCP (Drive, Slack, Sheets, calendar, email)

    Prefer structured sources when permissions and coverage fit; connector/MCP does not guarantee safety.

  • 2 · Local files in a permissioned folder

    File access may be local; a cloud model or tool can still receive its contents. Check the actual data flow and approved destinations.

  • 3 · Plugin

    A package may include skills, connectors or tools; categories can overlap.

  • 4 · Browser use

    Use when structured sources lack suitable access/coverage or do not fit the job.

  • 5 · Computer use (driving the whole machine)

    Only when the browser isn't enough. The last resort.

Choose the narrowest access that supplies sufficient data and checkable results. Speed/stability depend on tool and job; lower tiers are not universally slower. The 5% alert threshold is an example for the owner to calibrate.

Takeaway

A scheduled task needs the right environment, runtime authority, owner, output checks, alerts and stopping; choose tools by data/access rather than an absolute order.

  • Check old information before reuse.
  • Handle leaked keys with revocation/rotation.

Key idea

Runs-for-you ≠ shareable

A personal skill carries implicit assumptions (file paths, accounts, templates) that are only true on the author's machine. Packaging a skill means making those assumptions explicit and shipping them alongside the skill in a self-contained folder, so it no longer depends on any one person's setup.

Relative paths, not your machine's paths

Use relative paths for portable assets. For external sources, document versions, approved paths/connections and access checks. Never bundle credentials, secrets or private data exports.

A README covering run conditions and dependencies

What someone else needs before they hit run

  • Connector / account: what's required (e.g. CRM staging, runner logs in themselves).
  • Environment: where it runs (Cowork · desktop app · staging only).

Personal skill · runs only on your machine
  • References absolute paths on the author's machine
  • Field-map / templates scattered across a personal Drive
  • Only the author knows which connector / account is needed
  • Nobody knows which build is in use, or who changed what
Skill package · anyone on the team can run
  • Assets live inside the package, referenced by relative path

One single place the whole team pulls from: an internal Git repo, a team Drive folder, or packaged as a plugin (tier 3 in the tool priority: "a bundled skill + connector + subagent for one role"). Many skills together form a library; each person picks the skill for the job they need, without having to understand all of them.   • VERIFY: receive raw/clean/rejected, map/criteria, keyed baseline and fresh export. Check full partition, every keyed field, extra keys and baseline; the full clean/target diff must be empty. Logs support audit; rejected never excuses accepted diffs.
  • Only conclude "done" when the full clean/target diff.csv is empty, the source partition is complete and the baseline is protected. rejected.csv explains excluded source rows, never accepted/target differences.

Lab B grading rubric

Level Score Criteria
Fail 0 Accepts completion without evidence, a nonempty full keyed diff or 10/10 against the map; count does not identify the cause.
Basic 1 Has evidence but misses a phase (usually missing OBSERVE or the pilot is skipped).
Pass 2 All phases/gates; accepted 1001/1002/1008, correct 7 rejected IDs; all 10 partitioned exactly once; empty full keyed diff; protected target baseline.
Excellent 3 Pass + raise the 1005 mapping gap to its owner, test a crash after pilot and UNKNOWN commit, resume without duplicates/overwrites; state binds source hash/map version and has been reconciled.
Expected answer
  • 3 rows clearly valid: 1001, 1002, 1008.
  • 6 rows clearly rejected: 1003 (missing source), 1004 (email duplicates 1002), 1006 (malformed email), 1007 (missing phone), 1009 (source not in the list), 1010 (date 32/03 doesn't exist).
  • 1 disputed row: 1005, also rejected, but for a completely different reason (see below). Total rejected.csv: 7 rows.

Row 1005: phone 84905678901 → 0905678901 has 10 digits and is valid under the map. Reject only because source “Giới thiệu” is outside the closed enum; do not translate it into referral. Raise a possible map revision for a future run while continuing accepted rows under this run’s approved contract.

Notice the shape of that answer: the job keeps running and the human still gets asked. This is exactly the pattern from Lesson 2.2: for a job that allows exceptions to be split off, replace "stop the whole job" with "write the record to rejected.csv with a reason and continue with the valid records". Halting an entire job over one row is a very expensive way to ask a question you could answer later; and if the AI translates "Giới thiệu" → referral on its own and moves on silently, that's failure 07 (Lesson 4.2) in its subtlest form: this time it guessed right, next time it guesses wrong and no one knows.

The key point when grading

Explain every row by the field map and satisfy the full rubric. Correct 3/7 counts alone are insufficient for Pass. Excellent additionally requires raising 1005, demonstrating crash-after-pilot recovery and reconciling UNKNOWN outcomes without duplication or overwrite. Migrating 10/10 violates this fixture’s field map.

Takeaway

Lab B: 3 accepted/7 rejected with correct reasons, complete source partition, empty full keyed diff and protected baseline; no repeated pilot on resume.
