Module 01 · Part I

Retrieval foundations

Before adding any layer, understand why retrieval exists, its simplest form, and how to tell whether a change is actually better. These four lessons go hallucination → naive RAG → chunking → evaluation/ablation, establishing the baseline for every later layer.

Lesson 1.1

Why retrieval is needed — the hallucination problem

About the example system in this course

Every concept is mapped against an example multi-tenant chatbot platform (many organizations, each with many chatbots, each with many users). This is a system illustrative for teaching purposes: every product name (Demo AM, Demo Media…), number, and parameter (cosine thresholds, k=60, cache-hit rates…) is an example value, not the operational or real customer data of any organization.

By the end you can
  • Explain why an LLM answers confidently even when wrong, and why that is a problem for a B2B product.
  • Name the three RAG stages and separate retrieval failures from answer-generation failures.
  • Explain why probabilistic generation can produce unsupported claims.

A B2B chatbot is asked: "Does Demo AM have a free trial?" It answers confidently: "Yes, 7 days free." It should be 14 days. The answer is wrong despite its confident wording. For a product where users ask in order to make a purchase decision, incorrect information can affect the user’s decision.

That's because an LLM is a probability machine over tokens. It produces smooth, plausible text regardless of whether the underlying fact is right or wrong. Retrieval-Augmented Generation (RAG) is the answer architecture: before the model writes, search a chosen knowledge base, hand the model the relevant passages, and tell it to answer only from those passages (with citations). The pipeline has 3 jobs:

  1. Index: turn knowledge into a form that supports cheap similarity search.
  2. Retrieve: the right passage for any given question.
  3. Ground: anchor the model's answer to those passages, with citations.

This course focuses on retrieval, one common failure class to measure separately. Even with the correct authorized source, a generator can change “14 days” to “7 days”; use separate retrieval and answer metrics to locate the failure.

A model to remember

RAG places relevant passages in context before the LLM generates an answer. Check both the retrieved passages and whether the answer follows them.

Takeaway

An LLM is a probability machine: confident prose is not proof of truth. Retrieval is loading the facts before answering, not forcing the model to "know".

Quick check

The corpus fits in the model context. What determines whether to retrieve or include it whole?

Lesson 1.2

Naive RAG — embed everything, find by cosine

By the end you can
  • Draw the 4 steps of naive RAG and explain the relation between meaning and vector position.
  • Explain why the query must be embedded with the exact model that embedded the chunks.
  • List 5 failure classes to evaluate in naive RAG and match them to possible changes.

Two products with near-identical names: "Demo AM" and "Demo Media". Naive RAG embeds both; because they share a brand family, their vectors sit close together in space. A user asks about Demo AM, the system returns a Demo Media chunk. Evaluate entity discrimination through lexical retrieval, metadata and entity planning.

The simplest RAG you can build has 4 parts:

  1. Cut each document into fixed-size chunks (e.g. 1,000 characters).
  2. Run each chunk through an embedding model: a function mapping text → a high-dimensional vector (e.g. 1,536 floats with text-embedding-3-small; the 2025–2026 models differ in both dimensionality and quality: voyage-4, gemini-embedding-2, Qwen3-Embedding, EmbeddingGemma).
  3. Store (chunk_text, vector) in a vector database.
  4. At query time, embed the question with the same model, find the K nearest vectors by cosine similarity, and hand those chunks to the LLM.

Vector search relies on this relation: text with the same meaning ends up geometrically close even when the words don't match, so "free trial" embeds near "no-cost evaluation period".

Matryoshka-trained models support shorter vector prefixes. For example, EmbeddingGemma supports truncation followed by renormalization; do not apply it to an arbitrary encoder. Int8/binary values use 4×/32× less raw payload than float32, excluding index/metadata overhead. Quantization can lose candidate recall; reranking only reorders retrieved candidates. EmbeddingGemma.

Suppose your only document is a PDF Demo-AM-pricing.pdf. Naive RAG cuts it into 3 chunks of 1,000 characters, embeds 3 vectors, the query "free trial?" → embed 1 vector → cosine sim against the 3 chunks → take the top 1 → send the chunk + question to the LLM with "Answer using only this passage." Total infrastructure: one Postgres table with a vector column.

Where this breaks

Lesson 1.3

Chunking — don't cut a table row in half

By the end you can
  • Explain why fixed-size character splitting breaks meaning (tables, sentences).
  • Apply natural-separator chunking and pick a sensible size/overlap.
  • Check embedding-token limits and split overlong tables while retaining headers.

A document has a pricing table: | Plan A | $9 | … | Plan B | $19 | …. Naive chunking splits every 1,000 characters and cuts right through a row: | Pl / an B | $19. That chunk's embedding represents nothing complete. A chunk is the atomic unit of retrieval: missing information in a chunk can reduce retrieval quality in later stages.

Before chunking there is extraction, and it breaks first. A multi-column PDF reads out zig-zag, a table flattens into one long line, a scan with no text layer needs OCR, an HTML crawl drags in nav and footer. A good chunker cannot rescue broken extraction: open your 5 hardest documents and read the extracted text with your own eyes before blaming the splitter.

The fix is natural-separator chunking: follow a hierarchy of separators, falling back to character cuts only as a last resort. The hierarchy: paragraph → line → sentence → word.

Two more knobs: size and overlap

Chunk size trades context-per-chunk against retrieval precision. A large chunk carries more context but dilutes the embedding signal across several ideas. The example platform uses 1500/300 for files and 1000/200 for web pages (web is smaller because pages are short and more topically focused).

Overlap guards against a cut landing in the middle of an idea. A 300-character overlap → a sentence near the boundary appears in both adjacent chunks; whichever chunk gets retrieved, the sentence is still there. Example: "…14-day trial. After that, your team is billed monthly." No overlap: chunk 1 ends "14-day trial.", chunk 2 starts "After that…" → the link is severed. Overlap 300: chunk 2 starts "…14-day trial. After that…" → the antecedent is preserved.

Anti-pattern

Character-based defaults reduce coupling to one tokenizer, but token-based splitting is also valid. Always check the embedding model’s token limit. Prefer document structure; split an overlong table by rows with repeated headers. The example1500/300 and1000/200 settings are synthetic starting points to validate.

▶PracticeMeasure the chunk-length distribution of your current corpus
Export the length of every chunk in one chatbot, plot a histogram, then hand-count how many chunks start or end in the middle of a table row. If that number is not zero, you just found a retrieval bug before adding any layer at all.
Takeaway

Prefer structural boundaries, check the embedding model’s token limit, then evaluate size and overlap. Twenty percent overlap is a trial setting, not an optimum.

Quick check

Why not set50% overlap by default?

Lesson 1.4

Evaluate before layering — measure retrieval before upgrading

By the end you can
  • Build a small evaluation set that represents real queries and important failure modes.
  • Separate retrieval quality from answer quality with the right metric for each layer.
  • Run one-change-at-a-time ablations and remove layers that create no measured lift.

Hybrid search, rerankers, and multi-query can make an architecture diagram look more “production” without making the product better. Without a fixed baseline, every new layer only tells you the system is different, not whether it is better, more expensive, or fixing one segment by breaking another.

The minimum eval set before optimization

Start with roughly 30–100 representative queries from real logs and domain experts. Each row keeps the query, relevant chunk/document IDs (qrels), expected evidence or answer, segment, and failure tag. Include both easy cases and the groups that tend to fail: similar proper nouns, typos, multilingual queries, stale/current documents, no-answer cases, ambiguous queries, and sources containing malicious instructions. Synthetic queries can fill coverage gaps, but someone who understands the corpus should review a sample before the set becomes a gate.

Layer to measureQuestionStarter metrics
RetrievalDid the right evidence appear, and did it rank early enough?Hit/Recall@K · MRR · nDCG@K
GenerationDid the answer use the evidence, answer the question, and cite the right source?Faithfulness/groundedness · answer correctness/relevance · citation correctness · abstention
ProductionWhat did that quality cost?p50/p95 latency · cost/query · error/timeout rate

Synthetic fixture: each of 5 queries has exactly one relevant canonical chunk. First-relevant ranks are 1, missing,2,1,3: MRR=(1+0+1/2+1+1/3)/5=0.5667≈0.57. Hit@5=4/5=0.80; it equals mean Recall@5 only under this one-relevant-item assumption. With gold{A,B,C} and retrieved{A,C}, recall=2/3 while hit=1. Evaluate no-answer queries separately for abstention. Select layers on validation, reserve an untouched final test and compare paired query outcomes; related variants need group-aware uncertainty. Adding Error Bars to Evals.

Do not collapse this into one “RAG score”

Correct retrieval plus a wrong answer points to the generator or prompt; wrong retrieval plus a plausible answer is a well-disguised hallucination. Keep component metrics so you know where to intervene. An LLM judge helps with faithfulness and relevance, but calibrate it against a human-labeled slice rather than treating its score as ground truth. Separating retrieval, generation, and efficiency is also a central axis of this 2025 survey of RAG evaluation. When you want something off the shelf: RAGAS and TruLens for faithfulness/answer relevance, BEIR and TREC-RAG for public retrieval benchmarks. Use them to bootstrap an eval set, not to replace your corpus's own. A public benchmark contains none of your tenants' proper nouns.

Ablation: compare benefit with cost

  1. Run the naive baseline and save its config, corpus version, model/version, K, latency, and cost.
  2. Enable exactly one change (hybrid search, for example) and rerun the same set.
  3. Read by segment, not just average: did proper nouns improve while multilingual queries regressed?
  4. Keep it when target lift justifies regressions and cost; otherwise revert it. No threshold is universal across corpora.
▶PracticeWrite 30 queries + qrels from last week's logs
Open last week's conversation logs, take 30 real questions, and for each one write down the chunk/document ID that should have been returned. That is your first frozen eval set. No tooling needed yet: a CSV file is enough to run the first ablation.
Takeaway

Evaluate each change with a frozen eval set + component metrics + budget gate, and a layer with no lift gets removed.

Quick check

After enabling a reranker, answer faithfulness rises, p95 latency triples, and Recall@10 stays flat. What is the best conclusion?

Module 02 · Part II

Identifying & fusing retrieval

Naive RAG breaks on identifying chunks and fusing signals. This module adds metadata, a parallel lexical path, RRF to fuse two rankings, and multi-query expansion: four layers fixing four different failures of plain cosine.

Lesson 2.1

Metadata — a chunk is not just text

By the end you can
  • Distinguish the 3 roles of metadata: filter, boost, route.
  • Decide when a metadata field should filter, boost, or both.
  • Explain why you shouldn't copy the whole entity catalog into every chunk.

A chunk says "$9 / seat / month". The vector says "this chunk is about pricing". But pricing for which product? The chunk doesn't know where it came from, when it was updated, or whether it deserves to rank higher than its siblings. The example pipeline carries a typed metadata contract alongside the vector.

Each chunk carries a metadata object built by a metadata service (example), with fields such as: sourceId, sourceName, sourceType (pdf), trustLevel (canonical | authoritative | standard | derived), sourceRole (product | pricing | policy | promo | release_notes…), canonicalSource (bool), intentAllowlist (["pricing","capability"]), entities ([{entityId:"demo-am",name:"Demo AM"}]), sectionTitle, keywords, updatedAt.

Metadata serves 3 functions in retrieval:

  1. Filter: return only chunks the user is allowed to see (tenant/ACL and publication state; language follows corpus policy).
  2. Boost: a canonical chunk outranks an equally-similar chunk from a promo page.
  3. Route: a query classified as pricing intent → prioritize chunks with sourceRole=pricing or an intentAllowlist containing "pricing".
Design rule

Source-level metadata lives in the source config (the official catalog); chunk-level metadata stores only what is local to that chunk. Copying the whole entity catalog into every chunk turns routing pages and tables of contents into false positives: they carry the same entity boost as a real description. Keep chunk metadata narrow.

Server-derived tenant/ACL constraints apply before ranking. Language filtering follows the product’s coverage requirements, not a universal rule.

Takeaway

The vector says "this chunk is about X". Metadata says "this chunk is from the official pricing page, updated Tuesday, mentions Demo AM". These attributes support ranking by source, version and entity.

Quick check

A denied-tenant chunk is highly relevant. Should its metadata filter become a boost?

Lesson 2.2

Hybrid lexical — BM25 catches what vectors miss

By the end you can
  • Explain why vectors collapse similar proper nouns into a hard error.
  • Run a lexical path (tsvector + GIN) alongside the vector path and say why 'simple' beats 'english'.
  • State why you can't drop the vector, and when lexical fails.

A user types "Demo AM", a proper noun whose meaning is… "Demo AM". An embedding is trained to compress meaning, which is the right goal for most queries and the wrong one here. It pulls "Demo AM", "Demo Media", "Demo Group" close together because they share a brand family. From the user's point of view, retrieving the wrong sibling is a hard error.

The classic fix is BM25 (Best Matching 25), a lexical ranking function over 30 years old (Robertson & Walker, TREC-3, 1994): it scores a chunk by the frequency of the query's terms (literal words), weighted by how rare each term is in the corpus (IDF), decaying with chunk length. BM25 doesn't know meaning; it knows literal token overlap, exactly the property you want for proper-noun/identifier queries. Postgres has a close cousin: tsvector + ts_rank_cd + a GIN index, with no separate Elasticsearch cluster needed.

The tsvector pipeline in Postgres:

-- add column + GIN index
ALTER TABLE document_chunks ADD COLUMN search_vector tsvector;
CREATE INDEX ... USING GIN (search_vector);

-- populate on insert
UPDATE document_chunks SET search_vector = to_tsvector('simple', content);

-- at query time: rank by ts_rank_cd
SELECT id, ts_rank_cd(search_vector, query) AS score
FROM document_chunks, to_tsquery('simple', 'Demo & AM & trial') query
WHERE search_vector @@ query ORDER BY score DESC LIMIT 20;
Why 'simple' not 'english'?

The 'english' dictionary stems ("running" → "run") and drops stopwords: good for English prose, bad when half the corpus is Vietnamese and the other half contains brand names. 'simple' tokenizes + lower-cases without stemming, keeping proper nouns intact across languages.

▶PracticeRun to_tsvector('simple') over 100 real chunks
Take 100 chunks from a live chatbot, populate search_vector, then pick 5 proper-noun queries and put the lexical top-5 next to the vector top-5. Wherever the two lists differ is exactly the recall the lexical path is adding.

The SQL below is illustrative: enforce a server-derived authorized scope and bind query parameters. PostgreSQL ts_rank_cd computes cover-density ranking, not BM25; a BM25 engine requires its own implementation. PostgreSQL.

Takeaway

Vectors are good at meaning, bad at identifiers. A parallel BM25 catches the proper nouns vectors collapse. Lexical fails on rephrasing, so you need both.

Quick check

Lexical catches identifiers so well. Why not drop vector search entirely?

Lesson 2.3

Reciprocal Rank Fusion — merging two rankings without normalization

By the end you can
  • State why adding the two rankings' scores directly fails (different scales).
  • Apply RRF: 1/(k+rank), k=60, dropping score and using rank.
  • Explain RRF's behavior as k→0 and k→∞.

You have a vector top-20 and a lexical top-20. How do you merge them into one top-20? The naive merge = add the two scores. It fails immediately: cosine ranges −1..1, ts_rank_cd is 0.001..50+. Adding directly → the larger scale always wins. You'd have to z-normalize, handle the edge case when one list is short, and recalibrate when the corpus changes: an endless tuning problem.

Reciprocal Rank Fusion (RRF) sidesteps this by ignoring score entirely and using only rank:

RRF(d) = Σ over each ranker r:  1 / (k + rank_r(d))

Use k=60 as a starting example, not a universal optimum. A document absent from a list contributes0. The original authors selected60 in a pilot and retained it during validation. RRF original paper.

One concrete number: chunk-A is rank 1 on the vector side → 1/(60+1) = 0.0164, and rank 2 on the lexical side → 1/(60+2) = 0.0161, so RRF(A) = 0.0325. chunk-F appears only at lexical rank 3 → 1/(60+3) = 0.0159. It still survives, just ranked lower. The numbers in Figure 2.3 are exactly those values, not cosine or ts_rank_cd. One detail that is easy to miss: chunk-D (vector rank 4) and chunk-G (lexical rank 4) both come out at 1/64 = 0.0156. A tie needs a deterministic tiebreak, by chunk id for instance, or the ranking shifts between runs.

Takeaway

RRF drops score and uses only rank: 1/(k+rank). No score normalization; k=60 was selected in the original study and remains a starting value to validate on your corpus.

Quick check

At k=0, compare one rank-1 hit with a document ranked2 in both lists.

Lesson 2.4

Multi-query expansion — ask one question four ways

By the end you can
  • Generate 4 deterministic query variants (original, entity-anchored, intent-anchored, paraphrase).
  • Compare a transparent bounded rule baseline with LLM rewriting on the same validation set and budget.
  • State why you must cap the number of variants and cache embeddings.

A user types "trial?". One word, an index of 10,000 chunks, many mentioning "trial" in passing. Not enough signal. The fix: expand 1 query into several variants, run all of them, fuse the results. The example platform expands deterministically (no LLM round-trip), at most 4 variants:

  1. Original: the literal text the user typed.
  2. Entity-anchored: add the entity the planner resolved, so "trial" becomes "Demo AM trial" if the context says we're talking about Demo AM.
  3. Intent-anchored: pricing intent → add the anchor "price plan cost subscription".
  4. Paraphrase: a deterministic rewording (multilingual anchor: a VI query gets an English form added for English website chunks).
Watch the cost

4 variants × 2 paths = 8 retrievals per query. Each is cheap on its own, but at scale you need: (a) cache embedding vectors per variant (variants that resolve to the same string don't re-embed); (b) a hard cap on the number of variants. The example platform caps MULTI_QUERY_MAX_VARIANTS = 4.

Takeaway

Four rule-based variants avoid a rewrite-model call but add searches. Measure recall, query drift, total cost and latency before keeping the configuration.

Quick check

Why try a bounded rule-based expander as a baseline?

Module 03 · Part III

Advanced retrieval quality

You have recall; now raise quality. Contextual chunking fixes lost context, cross-encoder rerank fixes bi-encoder blurriness, CRAG knows when retrieval has failed, and self-corrective retrieval retries once within authorized scope.

Lesson 3.1

Contextual chunking — prepend "what this chunk is about"

By the end you can
  • Explain why a chunk from the middle of a document loses context ("the" = who?).
  • Apply contextual chunking: the LLM generates context → prepend → embed.
  • Give 3 reasons to store the context prefix in metadata (audit, re-embed, cache).

Look at a chunk taken verbatim from the middle of a PDF:

"$9 per seat per month, billed annually."

What is it about? Can't tell. "per seat" refers to a product named on a previous page that the chunker threw away. This chunk's embedding sits near every other chunk that says "$9" or "per month", across every product. At query time, a user asking "Demo AM price?" may not match it. The Anthropic 2024 result: one LLM-generated context sentence, prepended before each chunk then embedded, cuts retrieval failure by 35% (5.7%→3.7% at top-20; this figure is contextual embeddings alone; up to 49% when combined with contextual BM25).

Contextual chunking fixes this at ingestion, not retrieval:

  1. For each chunk, call a fast LLM to write 1–2 sentences of "situating context" from the chunk + a document summary.
  2. Prepend the context before the chunk text before embedding. The vector reflects "this is the Demo AM pricing section" + the original prose.
  3. Store the original prose unchanged. The context is for embedding; the chunk text handed to the LLM at answer time is the raw prose + citation metadata.
Different from attaching a section title to a chunk

A section title is static/structural. A generated context prefix knows the whole document and the chunk's role: "This passage is from the 'pricing' section of the 2026 Demo AM product brief, comparing the Pro and Enterprise plans." That's information the chunker can't recover from a lone chunk.

The35%/49% figures are Anthropic’s2024 top-20 retrieval-failure results, not a promised application improvement. Generated context must be checked against its parent source and regenerated when that source changes. Contextual Retrieval.

Takeaway

Parent-conditioned context locates a chunk before embedding. The35%/49% reductions belong to Anthropic’s2024 experiment; applications need their own eval and complete context-generation cache inputs.

Quick check

You already used the context prefix for embedding. Why also store it in metadata.contextPrefix?

Lesson 3.2

Cross-encoder reranking — scoring query/document pairs

By the end you can
  • Distinguish independent dense bi-encoding from joint cross-encoder pair scoring; measure quality/cost tradeoffs.
  • Apply a lexical/dense candidate funnel followed by pair reranking.
  • Select candidate count by quality and budget.

Candidate retrieval can use lexical ranking such as BM25 and/or dense retrieval. A bi-encoder separately encodes query and document for vector comparison; BM25 uses lexical signals and is not a bi-encoder. A cross-encoder jointly reads a query/document pair.

A cross-encoder scores a query/document pair jointly. It can improve ordering, at added computation. Use lexical and/or dense retrieval to form candidates, then validate candidate count and reranking quality on your corpus; top30→15 is this lesson’s synthetic setup.

Example: the query "How long is the Demo AM trial?". The bi-encoder top 5 mixes in a Demo Media trial chunk (close in meaning, wrong product; it never sees query and chunk side by side). The cross-encoder reads "How long is the Demo AM trial?" + "Demo Media evaluation is 7 days…" at once → recognizes the product mismatch → scores it low. The final top-1 is the real Demo AM trial section.

Late interaction, such as ColBERT(2020), retains token representations and combines their interactions at query time; document representations can be computed offline. Evaluate quality, index size and latency for the actual model, corpus and hardware rather than assuming a universal cost or quality ordering. Source read13 Nov2026.

Candidate retrieval may be lexical or dense; BM25 is not a bi-encoder. Top30→15 is a synthetic configuration. Scoring100 instead of 30 pairs means3.33× pairs, not a fixed latency multiplier; hardware/batching/model decide elapsed time.

Takeaway

Candidate retrieval determines which passages remain eligible for selection; reranking only reorders supplied candidates. Keep the funnel when eval shows benefit within budget.

Quick check

Lesson 3.3

CRAG — knowing when retrieval has failed

By the end you can
  • Classify retrieval into the 4 CRAG states and their corresponding actions.
  • Explain why "I don't know" preserves trust better than making something up.
  • Distinguish CRAG (classify after retrieval) from the clarification gate (before retrieval).
  • Draw the 3-gate control plane: clarify (before retrieval), G1 retrieval gate (after retrieval), G2 faithfulness gate (after generation). Say why production runs G1 before G2.

Even with reranking, the top result can still be garbage: the user asks about a topic the corpus doesn't cover, or the rerank scores are flat (nothing stands out). Handing garbage to the LLM → a confident wrong answer; the model doesn't distinguish low-confidence retrieval from high-confidence.

This lesson uses a four-state policy inspired by CRAG, not the paper’s original classifier. After hard authorization/publication filters, let n be candidate count and s the maximum valid score. Select floor f and high threshold h, with f<h, on validation; apply exactly one row below.

StateTriggerAction
confidentn >0; s ≥ hGenerate with citations; still check support.
moderaten >0; f ≤ s < hAnswer within supported limits if evidence suffices; otherwise abstain.
lown >0; s < fOne bounded retry; abstain/clarify if still weak.
emptyn =0One retry within hard scope; if still empty, abstain/clarify.
Distinction

CRAG handles the case where retrieval has already run but came out weak. The planner clarification gate (Lesson 4.1) handles the case before retrieval: if the planner sees an ambiguous query (two matching siblings), it asks for clarification before retrieval runs. Two gates at different stages.

Put CRAG in the bigger picture: a production pipeline has a quality control plane with three gates. The clarify gate sits before retrieval (4.1), G1, the retrieval gate, is CRAG itself, and a third gate this lesson hasn't mentioned yet, G2, the faithfulness gate, sits after generation because good retrieval still doesn't guarantee a faithful answer.

Correct, authorized, current evidence still does not guarantee a correct answer: the generator can change14 days to7. G1 runs before generation and cannot inspect an answer that does not yet exist. G2 checks support/citations afterward using rules, NLI or an LLM judge; checks can miss errors and need human-label validation. Gate costs depend on implementation.

Three anti-patterns when shipping a retrieval gate
  • Treating a score as truth probability. A high cosine or reranker score can still select the wrong sibling. Scores depend on model/corpus; select thresholds with validation labels, inspect segments and reevaluate after model changes. Validate calibration separately when probabilities are needed.
  • Empty, but the model falls back to its training data. "Not found" has to become "I don't know": general model knowledge overriding tenant knowledge is how you break B2B trust.
  • Low → opening an unbounded agentic loop. One bounded rescue (3.4) first; a free-running loop is paid for in cost, latency and non-determinism.

Two illustrative options when reranking is off: enable it for the scored segment or use degraded mode. Without scores, distinguish only empty(n=0 after hard filters) from nonempty-unscored; do not count “above-floor” candidates or assign confident. Missing/failed scores follow this mode too; log the trace and use the configured abstain/review policy.

Set thresholds with evals, not vibes

Choose score thresholds on validation, separated by relevant query segments; reserve final test for evaluation. Optimize the task’s quality, abstention and budget tradeoff. A higher answer rate can increase error exposure but does not prove fabrication. Calibrate scores against labels when probabilities are needed.

Finally, remember this lesson's limit: CRAG only classifies; on its own it fixes nothing. The corrective action lives in Lesson 3.4, and it is bounded: a classifier plus a bounded policy, not a free agent.

Lesson 3.4

Self-corrective retrieval — a bounded rescue loop

By the end you can
  • Separate soft retrieval choices from hard access/publication boundaries.
  • Design one bounded retry and an explicit abstention outcome.

A customer asks for a refund policy. The approved corpus has none; a draft says “100% refund”. A draft is not a hidden approved answer. The customer must not receive it simply because it is relevant.

A bounded rescue makes at most one retry after weak retrieval. It may broaden a soft query term or entity alias within the same permitted, approved and effective-date corpus. It never relaxes tenant, ACL, publication or effective-date constraints. Draft preview is a separate explicitly authorized reviewer mode.

StepDecision

A higher CRAG tier is a relevance signal, not proof of truth or permission, and cannot guarantee no degradation. Reuse compatible query embeddings when possible; a reranker may still cost a model call. The retry policy can be deterministic even when model scores vary.

Record query changes, allowed scope, selected source versions and selfCorrected=true. Compare the bounded retry against the baseline on validation data. Ferrazzi et al. report task-dependent tradeoffs: their agentic setup used 3.3× input and 1.9× output tokens on average; this is not a universal argument against agentic retrieval. Retry within the same authorized, approved corpus; a better score never overrides a hard boundary.

Lesson 4.1

Entity-aware planning — the production disambiguation layer

By the end you can
  • Explain why exact known aliases are a transparent baseline for this catalog, and when to clarify.
  • Apply the planner's 3 jobs: resolve, reject the sibling trap, clarify.
  • Describe how a resolved entity propagates down to multi-query/lexical/rerank.

Demo has dozens of products with overlapping names: Demo AM, Demo Media, Demo Social, Demo Group. Generic RAG retrieves whichever sibling vector-matches first. That's a quality bug, not a tuning problem.

The core idea: each source declares an entity catalog in its config. Each entity has a stable entityId, an official name, and a list of aliases. At query time, before retrieval runs, a planner matches the user's text against the catalog. The planner has 3 jobs:

  1. Resolve the user's text into ≥1 candidate entities, preferring an exact name/alias match over a single-token overlap.
  2. Reject the sibling trap: if the user types only "Demo" (a token common to every entity), that isn't enough evidence. A multi-word alias needs either an exact phrase hit or ≥2 alias-token overlap.
  3. Clarify: if two candidates are equally strong, return a clarifying question instead of running retrieval and getting an averaged answer smeared across the siblings.

When the planner resolves, the entity propagates down the pipeline as a hard signal: the multi-query expander adds the entity to the entity-anchored variant; lexical recall boosts chunks whose metadata.entities[] contains the entityId; the reranker sees the entity in the query, helping the cross-encoder's judgment.

Exact aliases are transparent for this catalog. BLINK is a counterexample to lexical-only entity linking: it uses dense retrieval and a cross-encoder. Clarify unresolved cases and compare alternatives on eval. Source read13 Nov2026.

Takeaway

For this known catalog, exact aliases are a transparent baseline before retrieval. Keep a trace and clarify unresolved ambiguity; evaluate other resolvers rather than assuming vectors are always the wrong tool.

Lesson 4.2

Production · Distillation — dedup + Q→A

By the end you can
  • Apply semantic dedup: cluster at cosine ≥ 0.85, tag dedupOf without deleting, then measure the lift on your own frozen eval set rather than borrowing someone else's number.
  • Explain why you tag rather than delete (reversibility/audit/recovery).
  • State why the Q→A index is only for high-value sources (cost).

Distillation reshapes the corpus so retrieval gets cleaner candidates: semantic dedup, an opt-in Q→A index, and a versionState lifecycle.

A · Merge semantic duplicates

A tenant often trains a chatbot on 3 overlapping sources: a PDF, a website, a hand-typed FAQ, all describing the same product. After ingestion, the index holds 5–15 near-duplicate vectors per fact. Top-K spreads the probability out, burying the canonical copy. A candidate dedup job runs after ingestion; editorial checks decide which candidates are equivalent:

  1. Propose clusters within compatible authorization, language and version scopes using cosine similarity ≥ 0.85, an illustrative threshold.
  2. An authorized editor checks meaning, effective version and provenance before selecting an approved canonical; trustLevel, priority, sourceRole and recency are supporting signals.
  3. Tag the non-canonical ones with metadata.dedupOf = canonical_id. Don't delete them; just skip them in retrieval (WHERE metadata->>'dedupOf' IS NULL).

Synthetic arithmetic:2042→1200 chunks excludes842 from retrieval, a41.23% reduction; this implies no quality gain. Select dedup thresholds on validation, retain reversible tags and evaluate query quality on held-out data.

0.85 is an example threshold, not the right one

“Refunds allowed” and “refunds not allowed” can share a topic while contradicting policy. Similarity cannot approve equivalence. The0.85 threshold is synthetic; review clusters, sweep on validation and evaluate held-out queries before enabling it.

B · Optional Q→A index (opt-in per chatbot)

The query is a question; the chunk is prose. Even with contextual chunking, the structural mismatch costs precision. The approach: for high-value sources (canonical pricing/policy/product docs), generate 3–8 question/answer pairs per chunk at ingestion. Store them as parallel kind='qa' rows next to the prose, with a parentChunkId back-reference so citations still point to the prose. Parallel, not a replacement: long-form queries still want the prose. The Q→A index supplements, fused via RRF.

Keep different ACLs, languages, effective dates and versions distinct. Similarity or recency cannot approve a source or establish supersession; canonical selection needs an authorized editorial decision with provenance.

Takeaway

Keep dedup reversible, preserve permission/version distinctions and measure held-out quality. Q→A supplements high-value sources with parent citations; it does not replace source prose.

Lesson 4.4

Production · Surgical curation — override, scopeMode, synonym

By the end you can
  • Apply per-page metadata override (sparse merge, the page wins per key).
  • Choose scopeMode single vs multi for a one-product vs many-product bot.
  • Calculate overlap/Jaccard and explain why either only proposes aliases for review.

E · Per-page metadata override

Source-level metadata (trust, role, intentAllowlist…) only goes so far. A Website source crawling 30+ URLs inherits one config for all of them, and it breaks when one URL in the source is noisy: /license-agreement/ is legal terms but keeps winning pricing queries because "license" appears hundreds of times.

The old workaround was "split it into a separate source", paid for with a whole new source to configure and maintain for exactly one page. The per-page solution is cheaper: a sparse JSONB metadata column on website pages. An operator opens a dialog on any URL row and overrides individual fields:

  • sourceRole: this page's own role (policy, pricing, product…).
  • intentAllowlist: which intents route to this page.
  • versionState: this page's lifecycle (4.3).
  • trustLevel: this page's own trust level.
  • canonicalSource: whether this page is the original.

A missing key inherits from the source. Null clears only where allowed; an empty list means empty. Merge at chunk build: {...sourceConfig, ...pageOverride}; present page keys win.

F · Chatbot scopeMode: single vs multi product

For a genuinely single-product bot, scopeMode can narrow the entity catalog. It must not pick a top entity merely to hide intent/version ambiguity. Confirm bilingual aliases with an editor; preserve clarification when direction, effective version or action differs.

G · Synonym entity merge (planner-side)

Compute name/alias token overlap to propose pairs for editorial review, without automatic merging. A has5 tokens {upgrade, foxora, novafox, v4, v5}; B has6 {chuyển, đổi, foxora, novafox, v4, v5}; intersection4 gives overlap4/5=0.80 and Jaccard4/7≈0.57. Threshold0.75 with intersection≥2 is a synthetic proposal rule; an editor checks product, action direction and version before approving a provenance-recorded alias/merge.

Overlap divides by the smaller set and penalizes the multilingual token tail less than Jaccard in this example. That arithmetic does not prove synonymy: upgrade and rollback share tokens but reverse direction. Measure proposal precision/recall and require review.

A missing override inherits; null explicitly clears only where allowed; an empty list means empty. Token overlap proposes aliases, it does not prove them: “upgrade V4 to V5” and “rollback V5 to V4” overlap heavily but have opposite intent. Validate direction/version with a domain editor. single_product narrows entity scope, not intent ambiguity.

Takeaway

Use explicit override semantics; scopeMode narrows the catalog; overlap proposes aliases. Merge after semantic/direction/version approval and clarify unresolved cases.

Lesson 4.5

Caching — cut token cost and latency

By the end you can
  • Distinguish provider prefix reuse from application answer/result caching.
  • Choose answer-changing cache inputs and test permission revocation.
  • Calculate a synthetic cost example and identify its excluded costs.

A cache hit reuses work; it does not grant permission. This example has many organizations, bots and users. Authenticate the caller before lookup and check current document permissions again before returning a hit.

LayerReusesHit condition
L1 exact answerStored answer; skips retrieval and generationMatching normalized question, authorized scope, source version and answer configuration
L2 semantic answer (opt-in)Answer to a similar questionSame hard scope plus validated similarity threshold; exclude personalized or consequential turns
L3 retrieval resultRanked chunks + plan + trace; generation still runsSame authorized corpus/version, resolved query and relevant conversation state
L0 provider prompt cacheComputation for a matching prompt prefixExact supported model/API eligibility, prefix, TTL and provider controls

Derive tenant, bot and authorization scope on the server. Answer-changing inputs can include corpus/version, prompt, model/configuration, resolved entities and conversation history. Hashing those inputs matches bytes; it does not prove that the answer is correct. Revoke or invalidate entries after permission/source/config changes. Single-flight lets one request rebuild an expired hot key while others wait; it does not change access control.

Stable content first

stable: approved shared instructions + authorized shared context
dynamic: visitor data + date + retrieved evidence + current question

Put changing content after the reusable prefix, using the supported API's controls. Keep visitor text in an untrusted user/data field. Prefix stability can improve reuse, but no hit is guaranteed. OpenAI's prompt_cache_key affects routing/accounting; it is not tenant authentication or document authorization. Provider organization/workspace isolation does not separate your application's customers inside one provider account.

Supported OpenAI GPT-5.6+ models also expose explicit breakpoints; older models differ. Gemini Interactions and Gemini 4 use implicit caching only, while supported older generateContent models also offer explicit caching. Claude minimum prefix lengths vary by exact model and hosting platform. Read the current model/API table instead of assuming a family-wide threshold.

A synthetic cost exercise

Choose 100 requests, each with 1,000 eligible shared input tokens. Suppose 20 cold writes cost 1.25 units per 1,000 tokens and 80 reads cost 0.10 units. Cost = 20×1.25+80×0.10=33 units versus100 uncached units:67% less for this shared-input portion. These are invented exercise prices and hit counts, not a provider quote, observed latency or whole-request saving; output, dynamic tokens, expiry and app-cache costs are excluded.

A public vendor benchmark is a different evidence category: AWS reports 56% hit rate and 92.6% cache-answer accuracy at threshold 0.95 over 63,796 queries/paraphrases, with 51.9% lower cost and 57.7% lower latency in its specified Titan/Claude/ElastiCache setup. Those values do not predict this application's performance.

Test the boundary

User A can read payroll and populates “What is An's salary?”; user B in the same bot cannot. B must receive no cached payroll answer. Revoke A's permission and repeat. Also test “its price?” after two different product histories. For a miss, inspect eligible prefix, actual bytes, TTL, routing and concurrency; zero cached tokens alone does not identify one cause. OpenAI prompt caching. Claude prompt caching. Gemini caching. AWS benchmark setup.

Takeaway

Cache within current authorized scope; measure hit rate, answer quality, full cost and latency before enabling it.

Lesson 5.1

The complete picture — every layer running at once

By the end you can

This diagram combines the course’s example layers; enable optional layers only when evals and the workload justify them. Compatible, currently authorized answer-cache hits (L1/L2) can reuse an answer; eligible retrieval-result hits (L3) can skip retrieval. Provider-prefix hits (L0) may reduce shared-input cost, subject to actual eligibility, hits and cache-write overhead. Repeating a question does not by itself authorize reuse. Retrieval supplies evidence; authorization and answer-support checks remain necessary. Measure quality, total cost and latency on the actual workload.

Choose a processing path for each query. Adaptive routing picks the path by difficulty: a simple lookup needs only vector + lexical; an ordinary question runs the full pipeline; and only multi-hop cross-document questions (where the answer is spread across several documents and has to be joined) justify considering agentic or GraphRAG. Even then, wait until evals (1.4) can answer "worth how many ×?", because the token cost of the agentic direction was measured back in 3.4.

Untrusted evidence is an attack surface

A crawled chunk may contain indirect prompt injection. Delimit/escape evidence as data, keep visitor text out of system/developer instructions, and enforce document/tool permissions in trusted code. Keep secrets out of model context. A newline-free malicious instruction still attacks the model: stripping control characters is not a security boundary. Red-team tests must check denied output/actions and data leakage, not only evidence-block formatting. These controls reduce risk; they do not guarantee immunity. OWASP LLM01:2025.

Takeaway

Retrieval layers, 1 pipeline, each layer fixing 1 failure of the layer below. Retrieval is also an attack surface: a better retriever raises recall AND the blast radius of a poisoned document.
