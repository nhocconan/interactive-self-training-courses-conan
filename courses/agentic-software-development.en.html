Module 01 · Part I

The 2026 Situation: agents, the real numbers, and the new bottleneck

Models, adoption metrics and total workflow cost.

Lesson 1.1

Models, harnesses and delegation risk

After this lesson you can
  • Separate the model from the harness and environment.
  • Place verification inside the loop and at acceptance.
  • Choose autonomy by risk, permissions and verifiability.

An agent fixes a timezone line and tests pass. Next you assign a 120-file migration and leave; the PR includes an unrequested schema change. The same model does not mean the same risk: scope, permissions and acceptance changed.

An agent can be viewed as model + harness: the model proposes actions; the harness supplies context/tools, executes under policy and records results. Gather → act → verify describes Claude Code’s loop, not a requirement that every agent has exactly three states. In-loop verification catches problems early; appropriate independent acceptance and gates still matter.

Fixture taskPilot authority/autonomyRequired evidence
Change log wordingLocal patch with proportionate reviewScoped diff; no behavior change.
120-file date-library migrationSeparate branch, no deploy; bounded task agentTimezone/DST, invalid dates and API compatibility tests; integrated review.
Production schema changePropose plan/patch without further authorizationOwner approval, tested migration/recovery, separate production authority.

Apply it

Use an autonomy ladder as team vocabulary: suggestions, reviewed task execution, then event-triggered workflows with gates. There is no required rung count or goal to maximize autonomy. Before a pilot state task, readable data, tools/rights, done criteria, budget and stopping mechanism. Ask or abstain when expected behavior is unclear. For data, reconcile raw fixtures with independently expected output and lineage; a build checks only what its tests encode. Track accepted output and total review/rework, not file or token count alone. Investigate harness, oracle and environment before blaming every regression on the model.

Primary source: Claude Code: How Claude Code works: “gather context, take action, and verify results”.

Takeaway

Autonomy is a decision about task, authority and evidence; green checks require correct oracles and risk-based acceptance.

Quick check

npm test passes in 3 minutes. Should a 120-file migration automatically proceed to deployment?

Lesson 1.2

Delegation gap: AI use and end-to-end delegation

After this lesson you can
  • Separate percentages of code, tasks, time and users.
  • Compute productivity from accepted tasks and total human effort.
  • Read uncertainty and selection bias before claiming an effect.

A leader sees a high AI-generated-code share and wants to halve engineering cost. Code share omits review, rework and customer value. First write down the numerator, denominator, follow-up window and sampling method.

Delegation gap describes the difference between AI involvement and handing off a whole task without intervention. The reported percentages may use different units, so subtraction need not yield a meaningful percentage-point gap. Self-reports measure perception; telemetry observes activity in its sampled systems; randomized trials estimate effects within studied populations and protocols. None automatically answers every team’s ROI question.

Apply it

METR’s early-2025 experiment reported tasks taking 19% longer while developers perceived a speedup. Its 24 Feb 2026 update gives time-change estimates of −18% for returning developers (CI −38% to +9%) and −4% for new developers (−15% to +9%). Both intervals include no change and slowdown; selection, retention and self-timing with concurrent agents make the current effect unreliable. This does not establish a switch to speedup. Do not subtract “20% faster” from “19% longer”: speed and time use different denominators. For your team predeclare task types, acceptance quality, total human review/rework time, tool cost and defect follow-up. Use a comparison group or random assignment where feasible. A simple before/after comparison needs confounders stated and is not a causal estimate.

Primary source: METR, experiment-design update (24 Feb 2026): “only very weak evidence”.

Takeaway

Adoption share is not productivity; ROI requires accepted output, complete costs and an explicit comparison design.

Quick check

AI participates in 80% of tasks. What follows?

Lesson 1.3

Throughput and total workflow cost

After this lesson you can
  • Separate throughput, quality and accepted value.
  • Diagnose queues using bounded system data.
  • Compare total cost before expanding a fleet.

Agents open PRs faster but release dates still slip. “Review is the bottleneck” is a hypothesis, not a conclusion established by rising PR count alone. Unclear specifications, slow CI and integration may also dominate.

Throughput is completed output per period; PRs opened measure arrivals. Higher throughput may accompany defects or lower-value work. Observational telemetry does not identify AI as the cause without examining task mix, adoption, staffing and follow-up.

Synthetic weekly fixtureBaselinePilot
PRs opened1020
Accepted PRs88
Human hours: writing + review + rework4050
Accepted output / human hour8/40 = 0.208/50 = 0.16; 20% lower

Apply it

Measure backlog age, review waits, CI time, rework and post-release defects. If review backs up while workers are idle, test smaller diffs or more review capacity; if CI dominates, improve CI first. Unmerged does not mean rejected. Report both human and model cost; benefit must be valued separately to compute ROI. Before/after comparisons can guide operations without establishing causation. A conceptual J-curve does not guarantee that an adoption loss will reverse.

Primary source: Claude Code: Best practices: “A prompt alone can’t guarantee either of those.”

Takeaway

Measure waiting and total effort; generated code is not proof of delivered value.

Quick check

Opened PRs rise 10→20, accepted output stays 8 and human hours rise 40→50. What follows?

Module 02 · Part II

Solo workflow: scoped planning and independent checks

Scoped planning, independent verification and tests with credible oracles.

Lesson 2.1

Explore → Plan → Implement → Commit — and when to skip the plan

After this lesson you can
  • Write a plan proportionate to uncertainty and impact.
  • Fix expected behavior before implementation.
  • Separate fixture reconciliation from comparison with prior output.

You ask for “rate limiting” and the agent guesses quota, identity key and window semantics. A long plan can still omit those decisions. The goal is checkable acceptance.

Explore → Plan → Implement → Commit is this course’s recipe. Explore existing contracts, resolve unknown decisions in the plan, implement within scope, verify and review before committing under delegated rights. Steps may be combined for simple, low-risk reversible work. A one-sentence diff can change permissions or money calculations, so brevity alone does not justify skipping a plan.

Apply it

A minimal plan states goal, non-goals, interfaces/input-output, expected cases, rights and rollback/stop. Exercise: calculate the table’s outputs yourself before the agent runs and freeze them in tests. Missing rounding, null or window-key policy requires the domain owner’s answer or abstention, not an invented rule. Choose a specification tool by workflow rather than generated file count. Measure time from requirement changes to useful feedback and total spec/code review effort.

Primary source: Claude Code: Best practices.

Takeaway

Planning reduces unresolved decisions; document length and artifact count do not establish quality.

Quick check

A new transformation adds 2 to rows 10 and 20. Which oracle fits?

Lesson 2.2

Verifiers: automating outcome checks

After this lesson you can
  • Define done using checkable outcomes.
  • Separate runnable checks from correct oracles.
  • Place verification and stopping at the right boundaries.

An agent pastes “all tests passed”. Was it a harness-recorded run, on which revision, command and environment, or text the agent wrote? Even authentic logs can accompany a weak suite passing incorrect code.

A verifier applies criteria to an artifact or external state: tests, data reconciliation, a database reservation or human rubric. One wrapper command improves repeatability; command count and speed do not establish oracle coverage. A deterministic check can consume noisy measurements or encode an incorrect assertion.

Apply it

Start with correct exit codes and a fixture containing a known defect; deliberately alter one value to confirm gate failure. Tie logs to inputs, revision and environment; verify final state independently of the answer. Hook effects depend on event: PreToolUse can block a pending call, PostToolUse cannot undo execution, and Stop may continue a conversation rather than block a merge. Protect important gates with runner/CI and branch policy outside worker control. Workers must not alter the oracle or remove tests to pass. Reviewers need spec/context and calibration for false positives and misses. Report “unverified” with a reason when evidence is insufficient.

Primary source: Anthropic, Demystifying evals for AI agents (09 Jan 2026): “The outcome is the final state in the environment”.

Primary source: Claude Code hooks reference: “effect depends on the event”.

Takeaway

Evidence needs run provenance and outcome checks; a green check is only as strong as its oracle and enforcement boundary.

Quick check

The agent pastes “tests passed” but the artifact has the wrong schema. What next?

Lesson 2.3

TDD, review and control

After this lesson you can
  • Distinguish three ways to use test-first with agents.
  • Check the oracle and the reason for red-green.
  • Read an exploratory evaluation within its scope.

An agent writes tests first, gets green and declares completion. You still need to know whether assertions encode intended behavior or repeat implementation logic. Writing order is a process signal, not a substitute for assertion quality and demonstrated defect detection.

TDD can mean a human supplies scenarios, a human reviews a failing test before the agent fixes code, or the agent runs red–green–refactor alone. The first two retain human checkpoints. Even the third can benefit from an independent test confirmed to fail on the right defect. Removing the human between steps does not logically remove every benefit of test-first.

Apply it

Böckeler compared a few small greenfield tasks with and without TDD instructions. She calls it exploratory: the sample is very small, quality mostly model-judged, and no run followed TDD perfectly. No discernible difference in that setup proves neither equivalence nor that every repo should drop TDD. Pilot workflow changes on matched tasks and budgets with shared independent oracles and held-out defects. Compare escaped defects, time and actual cost; cached tokens do not share one price. Mutation testing checks whether tests detect code changes; surviving mutants may be behaviorally equivalent or uncovered, requiring inspection. Static analysis, tests and review complement each other. Keep planning and human review proportionate to risk rather than mandating one universal pair of checkpoints.

Primary source: Birgitta Böckeler, TDD inside the agent loop (10 Aug 2026): “This is obviously a very small sample size”.

Takeaway

Evaluate tests by their oracle and detected defects; whether to use TDD is a hypothesis to test on your work.

Quick check

An exploratory eval found no clear TDD quality advantage. What follows?

Module 03 · Part III

Config as code: shared configuration in the repo

Instructions, effective permissions and reviewed shared configuration.

Lesson 3.1

CLAUDE.md / AGENTS.md: project instructions and limits

After this lesson you can
  • Separate contextual instructions from runtime rights.
  • Write concise, scoped and testable repo rules.
  • Verify loaded instructions rather than inferring from filenames.

You write “do not read secrets” in an instruction file, then grant broad shell access. The file communicates intent; it does not remove the process’s read rights. Investigate loading, conflicts, tool behavior and permissions before deciding an ignored rule is merely too long.

CLAUDE.md/AGENTS.md conventions depend on the harness. Current documentation distinguishes context from enforced configuration. Filenames, imports, precedence and scope can change; inspect the tool’s docs and what the session actually loads. “Nearest file always wins” cannot replace system/managed policy and user-instruction hierarchy.

Apply it

Exercise: write 5–10 lines naming commands, ownership, schema sources and done criteria; run a dummy task and inspect logs/diff. Keep cross-session knowledge; move long procedures into a skill or explicitly linked document. The documented under-200-line target is guidance, not a scientific standard or universal AGENTS.md limit. Review rules like code: owner, rationale and regression case. Enforce critical constraints outside the agent’s editable scope; more capital letters do not provide enforcement.

Primary source: Claude Code: Memory: “context, not enforced configuration”.

Takeaway

Repo rules supply context; verify loading and enforce critical constraints through rights and gates.

Quick check

A file says “never read .env” but the shell can open it. What follows?

Lesson 3.2

Three gatekeeping layers: rule, mode, sandbox

After this lesson you can
  • Distinguish tool policy, approval and sandboxing.
  • Test effective permissions with allowed/blocked actions.
  • Recognize deny rules do not cover every subprocess.

Approval prompts are noisy, so you want fewer. Begin with the task’s required rights and environment rather than disabling prompts and hoping the model distinguishes risk.

Tool policy governs calls; approval policy governs when a person or classifier is asked; sandboxing bounds process resources. API/database identity and authorization add another layer. “No prompt” does not imply “no sandbox”, and read-only does not mean every read command needs approval. Products and organizational policies combine these axes differently.

Apply it

Current Claude Code docs say Read/Edit rules cover built-in tools and recognized shell operations, but not every subprocess opening files indirectly. Thus Read(./.env) does not prove Python cannot read the file. Enforce filesystem boundaries through sandbox/OS rights; use dummy secrets in tests. Recheck effective configuration after mode or managed-policy changes. Hook events and failure contracts differ; PostToolUse observes an action already taken. Consider bypass modes only in authorized isolated environments, never as substitutes for narrow credentials or server authorization.

Primary source: Claude Code: Permissions: “For OS-level enforcement”.

Takeaway

Reduce prompts within authorized tasks while preserving real boundaries; verify rights with action probes.

Quick check

Read(.env) is denied but a script can open the file directly. What next?

Lesson 3.3

Onboarding: configuration, setup and permission checks after cloning

After this lesson you can
  • Separate shared, personal and managed configuration.
  • Verify effective configuration after cloning.
  • Keep credentials and telemetry within scope.

You clone a repo yet a colleague gets different commands and rights. Committed configuration improves reproducibility without installing dependencies, granting authorization, establishing trust or creating valid credentials.

Config-as-code is a versioned, owned, reviewed artifact. Claude Code project settings can be committed; local overrides are personal and must be ignored when manually created. Managed settings carry organizational policy. Precedence is key-specific: lists such as permissions.allow may merge rather than taking one highest file wholesale.

Fixture artifactSharingPost-clone check
Instructions + skillsCommit non-secret contentDoes the tool load the expected version and scope?
Project settingsCommit reviewed rights/hooksInspect effective config; probe allowed and denied actions.
Credentials + local settingsSecret store, separate identity, never committedLeast privilege, expiry/revocation and proper ignore.

Apply it

Exercise: on two clean environments use the same revision, run an allowed dummy command, try a denied dummy file and an out-of-scope API write. Record outcomes; inspect managed/local/CLI overrides and list merging when they differ. Do not copy production .env into worktrees; use development fixtures and separately issued narrow credentials. Masking covers configured tokens/paths, not every logging or tool route. Approve telemetry endpoints, data types and access; avoid raw secrets in commands/inputs. MCP project configuration needs separate trust and permissions; committing a declaration neither certifies the server nor grants authority.

Primary source: Claude Code: Memory.

Primary source: Claude Code settings: scopes and precedence: “Lists merge instead of overriding”.

Takeaway

Versioned configuration makes setup reviewable; effective rights, credentials and trust still require verification in the task environment.

Quick check

Two machines share project settings but have different rights. What next?

Module 04 · Part IV

Learning from failures: diagnosis, regressions and gates

Lesson 4.1

Rule accretion: updating instructions from failures

After this lesson you can
  • Diagnose before adding rules.
  • Turn repeated failures into regressions and gates.
  • Test whether instructions/controls change outcomes.

An agent repeats a mistake, so you add another instruction. Weeks later the file is longer and the error remains. More context helps a context failure; a wrong assertion or overpowered credential needs a different repair.

Rule accretion means promoting lessons into shared artifacts. “Second occurrence” is a suggested review trigger, not a reason to wait after a severe first incident. The four lenses below are course diagnostics, not an exhaustive taxonomy or diagnoses established by one symptom.

HypothesisEvidenceTrial intervention
Missing contextInspect files and instructions actually loadedShort scoped rule; rerun a held-out case.
Tool/oracle failureReproduce call, input and expected outputFix tool/check; confirm a known defect is detected.
Unresolved specTwo interpretations both fit the requestOwner resolves contract and edge cases.
Model/harness limitRule out budget, context, authorization and stopping errorsSplit task/change configuration and compare matched fixtures.

Apply it

Exercise: introduce a wrong-column fixture and confirm regression failure, repair the relevant tool/plan/rule, then rerun. Promote to a gate when the oracle is credible and an owner accepts cost. Deterministic hook execution does not imply noise-free measurement or correct policy. CI blocks merges only with required server checks outside worker control. If an agent can edit its gate, additional diff/policy protection is needed. Prune stale rules using evidence; do not delete regressions just to make a report green. Severe events may require revocation on the first occurrence before analysis and recurrence prevention.

Primary source: Claude Code: Best practices.

Takeaway

Lessons need the right causal layer, regressions and ownership; test enforcement rather than inferring it from “hook/CI”.

Quick check

An agent deletes out-of-scope data for the first time. Wait for a second occurrence?

Lesson 4.2

Memory: information retained between sessions and its limits

After this lesson you can
  • Separate instructions, auto memory and task state.
  • Promote personal learning into reviewed team artifacts.
  • Evaluate memory against an equal-budget baseline.

An agent remembers an old test command and repeats it after the repo changes. Memory carries information across sessions, but saved information can be wrong or stale. Persistence is not verification.

Instructions are maintained guidance; auto memory is agent-written notes; task state records current work. Instructions and memory are context, not runtime authority. Current Claude Code docs describe per-repository machine-local auto memory shared across worktrees, without automatic sharing to other machines/cloud. That default is not an impossibility theorem for every memory system.

ArtifactUseful contentCheck
Team ruleVerified test command and scopeOwner, checked revision/date; update when the repo changes.
Personal notePreferences and tentative learningsNo credentials; editable and removable.
Task ledgerCompleted files, checks and blockersReconcile with artifacts and logs, not narration alone.

Apply it

Exercise: store “test with npm test”, change a fixture repo to npm run test:unit, then start a fresh session. Check whether the agent verifies package.json or blindly follows the stale note. Add this case to memory evaluation. Compare memory/no-memory on matched tasks, model, context and retrieval budgets; hold out tasks not used to write the notes. Benchmark uplift does not directly imply team ROI. Record provenance, review expiry and deletion. Issue/web content must not silently become trusted guidance.

Primary source: Claude Code: Memory.

OpenAI dots can keep ongoing context across ChatGPT, Slack and Teams. A delegated worker still receives selected task context, not every past conversation. Compare the handoff in lesson 5.10; see dots tasks and memory.

Takeaway

Memory is sourced, expiring context; team learning requires verification, review and regression checks.

Quick check

Memory names an old command while the repo uses a different one. What next?

Lesson 4.3

Postmortems, golden sets and error budgets for agents

After this lesson you can
  • Turn an incident into an owned, checkable regression.
  • Distinguish pass@k, pass^k and the assumptions behind multiplying probabilities.
  • Separate a pre-release eval gate from an operational error budget.

An agent deletes a staging table. “Prompt more carefully next time” neither restores data nor prevents recurrence. A postmortem records impact, the timeline from logs, the permission mechanism, unknowns and an owned action with a checkable end state; it does not invent the model’s motives.

A golden set needs inputs, an independent oracle and a resettable environment. Add the incident as a regression; keep capability exploration separate so that an easy regression suite cannot masquerade as progress. One passing run does not establish stability; an incorrect test can also reject a valid solution.

Apply it

For heterogeneous tasks average pᵢ³ across tasks; do not cube the average pᵢ. For p₁=0.5 and p₂=1, mean p is 0.75 but mean pass^3 = (0.125+1)/2 = 56.25%. For dependent attempts, estimate the all-k success rate directly and report uncertainty clustered by task. Hard invariants such as “no writes outside scope” block immediately; noisy metrics need predeclared repetitions and comparison rules. Remaining budget is only one operational condition. New permissions require an accountable owner’s risk review and authorization.

Primary source: Anthropic, Demystifying evals for AI agents (09 Jan 2026).

Primary source: Google SRE: Embracing Risk: “request success rate”.

Takeaway

A postmortem produces a checkable regression; eval gates, repeated-trial consistency and operational error budgets answer different questions.

Quick check

An eval drops from 99% to 94%, below a local 98% gate. What follows?

Module 05 · Part V

Team + fleet: many people, many agents, one cadence

Measured WIP, worker contracts, runtime boundaries and bounded automation.

Lesson 5.1

Many people, many agents, one cadence: set WIP by review capacity

After this lesson you can
  • Apply Little’s Law using averages within one queue boundary.
  • Choose trial WIP from target lead time and measured throughput.
  • Separate unmerged work from rejected work.

You open ten PRs overnight, but have one reviewer and an old backlog. More agents may increase arrivals faster than service capacity; measure the queue before declaring review the only bottleneck.

WIP is unfinished work within a chosen boundary. Little’s Law relates long-run averages in a stable system: L = λW. L is average WIP, λ is completions/day, W is time spent inside that same boundary. Maximum capacity is not automatically observed throughput; an ever-growing overloaded queue is not a stable system.

Synthetic fixtureCalculationMeaning
Review lane completes 4 PRs/day; average WIP 4W = 4/4 = 1 dayTime in review, not the feature’s entire lead time.
Same throughput 4; average WIP 10W = 10/4 = 2.5 daysA comparison of hypothetical steady states, not a per-PR forecast.
Target W = 1 day; measured λ = 4/dayTarget L = 4 × 1 = 4 PRsA starting WIP for this lane.

Apply it

Start with few workers, separate file ownership and an integration owner. One owner per file reduces collisions but does not establish API compatibility. Set timeouts, budgets and a no-progress stop condition. “Three loops”, “3–5 workers” and reviewer/builder ratios are pilot settings to calibrate, not scientific constants. Track total human review and rework time, accepted output, backlog age and post-merge defects. Unmerged PRs may still be open or have insufficient follow-up; merge rate is not discard rate. Smaller scope and diffs may shorten queues without increasing headcount.

Primary source: Claude Code: Agent teams: “Agent teams add coordination overhead”.

Takeaway

Set WIP from measured flow and review capacity; Little’s Law requires a shared boundary and stable averages.

Quick check

A stable review lane completes 4 PRs/day; target average time in that lane is one day. Which pilot fits?

Lesson 5.2

Orchestration: briefs, permissions and integration

After this lesson you can
  • Write objectives, output format, tools/sources and task boundaries.
  • Distinguish a work contract from enforced permissions.
  • Compare fan-out with sequential work using accepted output and total human effort.

Three workers return green PRs using three incompatible state mechanisms. Each branch can satisfy its own brief while failing integration. The coordinator must agree interfaces first, assign ownership and accept the integrated result.

Orchestrator–worker is one architecture: a lead decomposes and synthesizes while workers handle narrow parts. Some systems return mostly summaries; others expose traces, messages or intermediate artifacts. One system’s reporting interface is not a universal limit on leads. A brief guides behavior; credentials, sandboxes, tool allowlists and policies outside the worker constrain actions.

Brief fieldExercise exampleCheck
ObjectivePOST /orders: 100 requests/minute per user; request 101 returns 429; reset after a fixed window.Use a fake clock to test boundaries, user keys and reset.
Output formatDiff + report tied to a revision, commands and harness-recorded exit codes.Inspect the diff and rerun checks; a self-reported transcript is not proof.
Tools & sourcesRead src/api, tests/api and approved policy; no new packages.Runtime permissions and logs must match the scope.
BoundariesOnly the two assigned files; no CI, DB or other agents; stop on no progress.An integration owner checks scope and unintended effects.

Apply it

Fan out only when at least two parts are sufficiently independent and expected benefit exceeds coordination cost. Two is a logical minimum, not an efficiency threshold. Worktrees isolate files on disk, not conflicting API decisions. Each branch needs suitable verification; reviewers need both the diff and enough spec/context to grade it. Separate context or a different model does not establish independent errors. Test model tiering against cost and escaped defects; the largest model need not always review. For data jobs, “done” requires valid output, schema/checksum and an independent oracle; file existence alone is insufficient. Compare with a sequential baseline on matched tasks: time to accepted output, total human review/rework, tokens and integration defects. A research benchmark gain is not a coding promise.

Primary source: Anthropic, How we built our multi-agent research system (13 Jun 2025): “most coding tasks involve fewer truly parallelizable tasks than research”.

Peer messages can resolve interface changes before integration. Use lesson 5.8 to practice that path. A message does not grant new authority. A worker is read-only only if the actual tool/process policy enforces it; a role label or worktree does not create that boundary.

Takeaway

A brief is a work contract; permissions, monitoring and integrated acceptance are separate controls.

Quick check

The suite missed three recent bugs. What precedes fan-out?

Lesson 5.3

Guardrails: permissions are control, prompts are suggestions

After this lesson you can
  • Set guardrails by impact, recoverability and authority.
  • Separate deny patterns from process-wide containment.
  • Drill stopping and recovery in isolated testing.

A worker has a staging token but production credentials are also on the machine. Despite “never touch prod”, an interpreter could read a credential and use another API. Risk follows effective access, not just tools named in the brief.

Blast radius is the scope of damage. Reversibility depends on backups, dependencies and recovery time: staging deployment may affect customers; force-push may be recoverable while objects/refs remain. The matrix supports environment-specific assessment, not immutable command classes. Separate identities aid attribution/revocation but still need least privilege and correct scope.

Fixture without real dataBoundaryProbe
Local-patch workerWorkspace/sandbox; no external write tokenAn API write attempt must fail.
Synthetic staging migrationAccount/DB isolated from prod; tested restoreDelete fixture rows, restore and reconcile.
High-impact actionDeny/allowlist, server rights and policy-based human approvalWorker cannot change the gate or grant itself rights.

Apply it

ASD’s 12 Nov 2026 guidance concerns cyber capability/cyber defence testing and explicitly excludes securing production deployments. Within that scope it warns against relying only on prompts/model safeguards and calls for network/tool/identity controls and tested shutdown. Apply those engineering principles in the course sandbox: probe denied read/write paths, check whether stopping prevents further effects, revoke a token and retry, then test restoration. Independent monitoring should record run/target/outcome without raw secrets. Production needs its own risk assessment and policy; this testing document is not deployment certification. Human approval can help yet suffer fatigue/errors; a high approval rate alone does not prove every approval is useless.

Primary source: ASD, Securing AI testing environments (12 Nov 2026): “do not provide sufficient technical containment on their own”.

Takeaway

Guardrails require tested boundaries, identity, observation and stop/recovery paths; prompts alone are insufficient containment.

A worker needs only staging. Which setup is checkable?

Lesson 5.4

Chief of Staff: roles, contracts and coordination

After this lesson you can
  • Translate persona job titles into tasks, permissions and acceptance criteria.
  • Choose topology by task dependencies rather than the largest benchmark gain.
  • Place human checkpoints according to risk and unresolved decisions.

You create PO, Designer, PM, BA, Dev and QA characters. Their messages are polite, but decisions remain incompatible. Role names aid communication without specifying who may edit what or who verifies the result.

A role-as-bundle specifies the objective, tools, effective rights, output and acceptance check. A persona supplies a viewpoint; it does not create expertise or an isolated identity.

Role labelCheckable bundleHuman intervention
QARead spec + diff, reproduce defects, report severity and evidence; do not edit another worker’s files.Conflicting oracle or an unverified finding.
DesignerReview the main flow, errors and accessibility against approved requirements.An unresolved experience tradeoff.
LeadTrack dependencies, assign ownership and integrate artifacts with separately bounded runtime rights.Scope changes, broader rights or conflicting objectives.

Apply it

Choose a setup for each fixture: (a) a schema migration whose later steps depend on the first decision; (b) independent accessibility and API reviews; (c) API/UI workers negotiating a shared field. Start with sequential execution for (a), separate first-pass reviews for (b), and targeted peer messages plus a versioned contract for (c). Change the setup if measured integration cost outweighs the benefit.

Compare time to accepted output, human review/rework, tool/model cost and escaped defects on matched work. Seed known bugs to check reviewer sensitivity; zero findings alone cannot distinguish correct code from missed bugs. Intent → plan approval → acceptance is this pilot’s cadence. Lesson 5.8

Agent messages: handoffs and contract revisions

By the end you can
  • Choose a suitable messaging route.
  • Match a message to its revision and evidence.

The API renamed a field, but the UI worker still sends “done” against the old version. If the lead reads only the final message, the two patches will not integrate. Messages need to identify the contract currently in force.

Claude Code supports messaging named subagents and messaging between sessions; every exchange need not become an agent team. In OpenAI Responses Multi-agent, send_message queues a message without starting a new turn; followup_task assigns more work and starts or resumes a non-root agent’s turn. Check the actual mechanism before waiting for a response. A message does not itself grant permissions or transfer the full context.

MCP provides tools, resources and prompts; A2A describes communication between agent services through messages, tasks and artifacts. They complement each other. MCP has a Tasks extension for deferred results, outside core since revision 2026-07-28; both client and server must declare support. “MCP is synchronous, A2A is asynchronous” is an inaccurate distinction. Native messaging does not itself establish A2A compatibility.

A message to adapt

This is a local recipe, not a protocol schema:

Message envelope
msg_id: msg-042
task: quota-ui; from: lead; to: ui-worker
revision: r18; contract: retry_after_ms = milliseconds
action: update UI + boundary test
evidence: contracts/r18.md

Your workflow records processed msg_id values so duplicate messages do not create duplicate work; do not assume runtime deduplication. After the deadline, ask for status before reassigning. When blocked, identify the missing input and the decision owner; on cancellation, record the final state and confirm the worker stopped.

Practice

Lesson 6.1

What changes in Agile when the team has agents

After this lesson you can
  • Keep useful process and diagnose the actual constraint.
  • Write DoD around outcomes, oracles and ownership.
  • Report throughput with quality, human effort and uncertainty.

An agent finishes code in a morning; the PR waits three days and needs rebasing. Velocity rises alongside failures. That does not establish that Scrum or story points must disappear; inspect actual work and queues.

DORA 2025 frames AI as an amplifier of organizational systems. This is a research interpretation, not a law that AI cannot create new capabilities. Story points may still represent uncertainty, integration and human effort; neither points nor tokens convert directly to productivity. WIP limits can operate in Scrum and Kanban.

Apply it

A pilot DoD requires explicit acceptance, independent test oracles that catch fixture bugs, appropriate diff ownership, revision-linked logs and no out-of-scope effects. Agent-generated tests can help when checked; human-written tests can be wrong. Mutation testing is an additional signal, not universal certification. Report time to accepted output, total human review/rework, cost and post-release defects. Surveys identify perceived friction without measuring counterfactual time savings. Before/after comparisons must disclose task mix, staffing, system and follow-up changes; use randomization or suitable controls when estimating causal effects.

Primary source: DORA, State of AI-assisted Software Development 2025: “AI’s primary role is as an amplifier”.

Takeaway

Fit measurement to tasks and risk; keep throughput beside quality and total effort rather than treating one ceremony or tool as the answer.

Lesson 6.2

Choose spec maintenance by feedback loop

After this lesson you can
  • Distinguish three levels of specification maintenance.
  • Measure feedback through accepted behavior.
  • Repair faulty artifacts and their generating process when needed.

A 14-page spec may help a complex interface or waste effort on a typo. A prototype in 20 minutes may teach quickly or show only the happy path. Document length and coding speed alone do not settle the method.

Böckeler describes spec-first, spec-anchored and spec-as-source as usage/maintenance choices, not a ladder to climb. Spec-first supplies task guidance; spec-anchored retains and evolves it; spec-as-source makes the spec primary and humans do not edit generated code by hand within that workflow. Her September 2026 author update notes that earlier tool examples changed, so do not memorize artifact counts from old tool releases.

LevelWhen requirements changeCheck
Spec-firstUse a spec for the task; retain or discard afterwards.Can intended behavior and key decisions still be traced?
Spec-anchoredMaintain spec and code together.Who updates the spec after code changes? Is drift detected?
Spec-as-sourceEdit spec and regenerate under the workflow.Have gates, diff/recovery and emergency changes been tested?

Apply it

Synthetic exercise: on matched quality, A takes 30 minutes specifying, 20 building, 40 reviewing/reworking; B takes 10, 20 and 80. Time to acceptance is 90 versus 110 minutes. Do not choose B only for its shorter spec stage. Assume no other waiting time. Also consider risk, traceability, maintenance and cost of mistakes; a fast loop does not waive payment-system gates. Improving harness/spec/tests can reduce recurrence, yet an incident may still require artifact repair, rollback and immediate user protection. “On the loop” is a useful perspective, not a ban on hand edits or intervention inside the loop.

Primary source: Birgitta Böckeler, Understanding Spec-Driven-Development (updated Sep 2026): “there are multiple implementation levels to it”.

Takeaway
